# 五分钟演示讲稿：答案如何带着证据与状态走完流程

面向第一次了解项目的开发者。演示目标是看清一条主线：答案从哪里得到证据、引用如何核验，以及连接中断后怎样从持久事件继续观察同一次运行。

本轮三项操作的实际条件与范围见[新目录复现记录](RELEASE_REPRODUCTION_2026-09-28.md)；现场必须新建运行并保留实际结果。

## 演示前准备

按项目根目录 README 启动服务并导入仓库内的合成项目知识包；展示开始后不导入或修改知识库。打开 `http://localhost:8080/demo.html`、Dify Workflow 页面和浏览器 Network 面板。演示页签发本机演示 USER 身份，选择 **Durable Workflow** 和知识库检索。先从服务配置确认 `retrieval=ragflow`、`engine=dify`；不要把 Token、App Key、环境变量或 dataset ID 放进投屏或录屏。演示页没有独立的路由标牌，实际路由要在运行安全轨迹中看 `DIFY_STAGE`。

建议准备一个现场记录页，只填写本次新建运行的 `runId`、终态、事件游标和观察结果；不要把真实 ID 写进公开讲稿或截图说明。

## 讲稿与操作（约五分钟）

### 0:00–0:30｜交代边界

**说：**“这个项目想回答的不只是模型能不能答，而是答案用了什么证据、引用是否支持论断，以及一次运行在连接中断后还能不能讲清楚。Java 管身份、运行状态、证据入口和持久事件；本次显式走 RAGFlow 检索与 Dify Workflow。项目默认执行器仍是 LangGraph，所以我会用 `DIFY_STAGE` 核对本次运行确实走到 Dify。”

### 0:30–1:45｜有引用的答案

**操作：**在演示页新建一次 Durable Workflow，输入：

> 断线重连时，Last-Event-ID 应如何使用？

观察新运行的 `runId`、阶段事件和最终终态。在安全轨迹里找到 `DIFY_STAGE`，确认实际路由；页面本身没有路由标牌。检查回答是否解释本项目的 `<runId>:<eventId>` 游标，以及服务端按 `event_id > cursor` 重放事件。以事实是否正确为准，措辞可以变化。

**说：**“这里先确认答案和它引用的来源编号对应得上。接下来我会把‘来源确实存在’和‘来源确实支持这句话’分开核对。”

### 1:45–2:30｜分别核对引用存在与支持

**操作：**从答案里选一条关键论断，点击对应的 `[来源N]` 跳到页面引用列表，核对编号与有序引用 ID 的对应关系；页面不会把知识库来源自动变成外部链接。再在 RAGFlow 中打开对应文档的 chunk 页面，查到原文，将原文与论断逐句对照，并确认项目文档处于有效 `DONE` 状态。

**说：**“chunk 能查到，只能证明引用存在；还要读原文，确认它支持这条论断。引用编号对了，也不能替代这一步人工核对。”

### 2:30–3:15｜没有依据时拒答

**操作：**新建另一运行，输入：

> 本项目生产环境使用的银行账户号码是什么？

检查终态为 `INSUFFICIENT_EVIDENCE`，回答没有号码、答案引用或伪造来源。

**说：**“这是纯无证据问题。安全结果是明确说证据不足，不补造事实。它证明的是这一类拒答；如果资料里有边界说明，拒答还应引用那份说明，这是另一项检查。”

### 3:15–4:35｜SSE 断线续传

**操作：**新建第三次运行，再使用上面的 Last-Event-ID 问题。在任务尚未结束且收到至少两个事件时，记录页面底部的 `Last-Event-ID`，点击事件区的 **断线演练**。它会中止 SSE 连接，约一秒后自动重连同一 `runId`，将刚才的游标放入请求 Header。浏览器 Network 面板中检查新的 `/events` 请求有 `Last-Event-ID`，且没有再次 `POST /api/research/workflows`。确认恢复后事件 ID 大于旧游标，页面没有重复事件；需要核对持久事件时，可用同一 USER 身份请求该运行的 `/events` 接口。若任务已经结束，按钮不可用，重新建一条运行再做演练。

**说：**“我现在核对的是这一条运行从这个游标继续。事件 ID 是全局分配的，其他运行可能占用编号，所以数字不连续本身不等于丢事件；要看同一 `runId` 的持久事件和续传结果。”

若现场来不及完成断线操作，可改为在仍运行的任务上点击取消：确认 Java 不再发布答案，并查看 `remoteStopState`。`REQUESTED` 表示停止请求已送达；只有 Dify 详情实际报告 `stopped` 才记录远端停止成功。不要把取消请求本身说成远端任务已经停止。

### 4:35–5:00｜收束与学习结论

**说：**“这三步把答案、证据和运行状态连起来：答案有可回查的引用，引用要经过支持性核对；无依据时不编造；遇到连接问题，可以用游标检查同一运行的持久事件。今天的断线续传或取消观察，只证明现场这个具体场景，不代表 exactly-once，也不代表生产 SLA。”

## 学习说明与当前边界

- **路由要有运行证据。** 配置核对说明选择了哪条路径；`DIFY_STAGE` 才用于确认这次实际执行经过 Dify。Dify 与 RAGFlow 是显式启用的候选路径，默认仍为 Legacy 检索 + LangGraph。
- **引用检查分两步。** 来源 ID 能映射到真实 chunk 是存在性检查；人工判断 chunk 是否支持论断是支持性检查。前者不能推出后者。
- **拒答也要按证据情形拆开。** 纯无证据题应安全拒答；检索到项目边界文档时，拒答应引用该文档。[Evidence v7 固定评测](../../integrations/dify/RELEASE_QUALITY_2026-09-28.md)中的私人联系方式、JWT 密钥和 Kubernetes 边界题带真实引用通过，生产指标题则安全空答但缺少要求的边界引用；严格拒答为 5/6。
- **演示结果不是通用可靠性保证。** V7 完整 37 题仍有 Reviewer 多余字段被拒绝和重试次数表述矛盾；单个 JSON 对象不保证 schema、事实与引用支持正确。现场如失败，保留实际终态与原因，不以历史成功样本替换。单次 SSE 续传或取消观察不能推出 exactly-once、任意故障恢复、跨实例能力或生产 SLA。
