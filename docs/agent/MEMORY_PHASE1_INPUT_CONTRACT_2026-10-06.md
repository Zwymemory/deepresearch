# 阶段一：显式研究项目记忆输入设计 v0.2

日期：2026-10-06（Asia/Shanghai）。本文件是阶段零形成的后续实现约定，**尚未实现或部署，不是现行 API 文档**。当前可调用接口仍以 [research-progress/1 交接](RESEARCH_PROGRESS_FRONTEND_HANDOFF_2026-10-05.md) 为准。

## 1. 一个可验收目标

用户选择已有研究项目，在新会话明确发起研究后，Agent 的真实规划调用输入包含经服务端重新核对、在预算内的原目标、已完成工作、未解决问题及来源引用。新运行归属于所选项目；历史进度不能代替本轮完成证明或证据。

范围限定为自主研究入口。普通 workflow、Dify 和同步 Single Agent 的旧行为保持兼容；本阶段不增加自动摘要生成、语义召回、自动成果写入或多 Agent 协作。

## 2. 用户动作和服务端边界

1. 现有 POST resume-context 仍仅创建空会话和返回项目历史；GET 用于恢复，不触发研究。POST 不幂等，前端禁止挂载、刷新、含糊网络失败后的自动 POST 重试。
2. 用户显式开始自主研究时，才提供来源项目选择。建议自主研究创建请求新增可选 `researchProjectId`；不传时保留当前行为。它仅是待核验的项目选择，客户端不能提交摘要文本、证据真实性、owner 或 tenant 作为权威输入。
3. 服务端从认证身份核对项目、目标 session 和来源 run 的归属。未知、越权或与其他项目关联的 session 统一按不可访问处理，不泄漏内容。
4. 不能仅把 `target_session_id` 传入现有 AgentRunService.create：当前实现会为新 session 建立新 project。阶段一必须增加“选择已有项目”的受控分支，使新 agent_research_run 指向所选项目，保留原研究的来源归属。
5. 同一目标 session 已在所选项目下运行时继续使用该项目；不得因省略选择字段而另建第二个冲突项目。与其他项目绑定的 session 拒绝切换。
6. 创建运行的既有幂等机制必须把项目选择纳入请求身份；相同 key、不同项目不能回放成同一个成功请求。GET 载入成功不视作该项目永久授权。

项目归属以 `agent_research_run JOIN agent_workflow_run` 所记录的 session/run/project 关系为后续会话的权威关系，原 `research_project.session_id` 保留其创建来源。所有自主研究创建路径在同一事务中锁定目标 agent_session 行、核对两种关系、决定项目并创建运行；事务失败整体回滚。对同一空 session、不同幂等 key、不同项目的并发请求只能一个项目胜出。不得改写原项目 session 来容纳续研 session。未绑定且不传选择时才沿用新建项目行为。

`researchProjectId` 是设计字段，实施时在自主研究专用 DTO 接收；不能无意让普通 workflow 接受它。现行 progress/resume 响应不更名、不添加虚构的保存时间。

## 3. 模型输入与审计记录

服务端新增独立的 prior_progress 输入区，不能把它并入已验证 evidence 或旧 user_memory 字符串。最小语义字段：

| 字段 | 约定 |
| --- | --- |
| schema_version | 新输入区独立版本，建议 `research-progress-context/1`；外层 decision context 如变更必须同步 Java/Python 契约和夹具 |
| context_kind / trusted_as_evidence | `prior_progress` / `false` |
| project_id | 服务端核验后的显式项目 |
| records | 每条保留 source_run_id、source_session_id、原目标、完成/未完成状态、关键约束、next_steps 和原始引用 |
| snapshot_sha256 | 对服务端当前 canonical 快照计算的内容指纹；不冒充记录修订号、语义版本或事实证明 |
| snapshot_instance_id / snapshot_revision | 服务端持久化的保存实例 ID 与单调修订号；用于识别删除重建及内容更改后还原 |
| selection | 候选数、入选引用及指纹、省略引用及原因、是否截减 |
| budget | 计数方法/版本、记忆输入用量、限额；估算与提供方实测分开 |

当前表没有这些生命周期字段；阶段一需增加最小内部元数据，不要求建立完整历史版本表。首次保存生成新 instance_id、revision=1；相同内容保存不变；每次内容实际改变 revision+1；删除后重新保存即使内容相同也生成新 instance_id。所有写路径必须遵守该规则，阶段零不预占迁移编号。运行和 checkpoint 引用 `(project_id, source_run_id, instance_id, revision, snapshot_sha256)`；每次检查数据库记录仍存在且所有标识匹配。因此 A→B→A 与删除→相同内容重建都不能恢复旧授权。

运行审计区分 selected（候选入选）、injected（规划调用边界实际收到）和 behavior_verified（行为对照证据）；不能把“出现于输入”或 markUsed 时间直接记成有效使用。保存最终输入 hash 和选取记录，不保存或展示模型隐藏推理。

## 4. 确定性筛选与预算

- 候选范围延续现行最多最近 20 条、过滤后不回填的边界。显式项目之外的记忆不参与补齐；没有有效快照时返回明确的上下文不可用状态，不悄悄退回无关记忆。
- 初始设计上限：最多 3 份进度快照，独立 prior_progress 区序列化为 canonical UTF-8 后最多 **16384 字节**，含该区结构及引用开销。先沿现行保存时间/运行 ID 顺序取候选；不把此规则叫语义召回。预算元数据固定 `method=utf8-canonical-bytes/1`、`limit_bytes=16384`，不称其为 4096 个真实 token。
- 全量实际 provider wire 仍按当前 `len(prepared.wire)+1024` 准入方法预留，并服从原运行剩余 input/output 预算；不能因局部记忆字节数较小而削弱原 ledger 防线。中文和非 BMP 字符覆盖字节边界；提供方实测 token 与本地估算继续分开。当前阶段不凭未经验证的 tokenizer 推算收益。
- 保留原目标、状态、未解决问题、争议与出处的完整语义。第一版不付费生成摘要；不能安全容纳的整条记录省略并记录原因，不能截断 JSON、改写为已完成，或只留下容易误导的完成结论。全部无法容纳时明确停止此记忆续研请求。
- 不增加现行自主研究 maxModelCalls=16、maxToolCalls=16、maxTokens=100000、maxInputTokens=64000、maxOutputTokens=16384 或 maxCostCny=1.0 上限；这些是源码配置上限，不能视为提供方实际费用保证。新增历史输入必须计入原预算预留。
- 每次实际规划调用及允许的重试都对包含历史的完整输入重新预留和结算；不能只在第一轮计入历史成本。纯操作结果回放不记录成新的模型消费。冻结选择/内容/hash 后再完成最终 wire 计量，后续内容变化不得沿用旧计量或旧派发许可。
- 16384 字节/3 条是本阶段建议的保守初值，属于后续实施契约参数，不代表已测得最佳值。验收覆盖 B−1/B/B+1、多条聚合、第二次规划剩余额度不足及 checkpoint 恢复；调参必须保留记录。

## 5. 使用前重验和证据边界

在创建运行时重新读取数据库；在每次将历史注入模型之前，以及恢复旧 checkpoint 后，重新核对快照存在性、身份/项目、来源和指纹。浏览器拷贝、旧 context_snapshot 或历史响应不能绕过删除和失效检查。

首版采取可复现的严格快照策略：instance/revision/hash 不匹配或记录不存在，停止本次记忆续研并返回结构化原因，要求重新选择；不静默替换新版本继续旧计划。来源在每次使用前按当前授权及状态复核，不承诺识别未留下任何版本/审计痕迹的历史临时状态变化。

新进度消费的来源复核需要在拥有的原项目/原运行只读权限下复用完整的 payload、原文 hash、回执及 source binding 校验；现有 progress GET 只核对部分引用字段。不能伪造原运行的活跃 grant，也不能把这项出处检查宣称为事实重新核验。原运行后续进展变化不自动刷新已保存快照，模型看到的是明确标记的历史。

规定可审计的派发授权点：在服务端事务中对当前快照/相关权威记录取得与删除或更新冲突的锁，完成校验后签发绑定 run、操作及完整记忆引用的单次许可，再提交事务；撤销先于该点提交时不能签发许可。授权点之后的在途请求（包括结果 UNKNOWN）可能无法撤回，必须保留并报告此边界；后续调用/重试/恢复不能沿用旧许可。不能持有数据库事务等待外部模型 HTTP 返回。验收用受控并发顺序验证撤销先于授权、授权后撤销以及恢复/重试，不作无法证明的“已删除内容从未在途”承诺。

旧完成项是“当时已有完成证明”，旧 next_steps 是线索，均不直接建立新 run 的完成状态。新报告需要的事实引用仍走当前 run 的授权读取、回执、证据核验及发布检查；过期或争议内容保留其状态。

## 6. 验收与实施分工

确定性验收必须捕获实际生产模型调用边界，覆盖：新 session/独立进程重启、精确注入与无记忆对照、待办延续控制链、越权/无关/失效拒绝、删除重建及 A→B→A、删除/授权时序、首次项目绑定竞争、checkpoint 恢复、逐次预算边界、仅载入零研究调用。固定模型替身证明链路，不证明真实模型智能或收益。

| 负责人 | 阶段一建议工作（未派发） |
| --- | --- |
| A：运行线 | 唯一负责自主研究请求 DTO、项目/run 绑定、幂等、Java→Python 输入与每次派发边界、预算与审计事件 |
| B：记忆线 | 负责服务端有效快照选择、内容指纹和使用前状态重验；不并行编辑 A 的共享 DTO |
| C：复审线 | 独立捕获输入、身份/撤销/预算负例及结果审查；不扩大旧 Round1 付费补测 |
| Claude：前端 | 在后端接口与合成样例可用后接入显式续研；根据注入状态展示，不因载入成功宣称使用；接收英文交接 |

阶段一开始前先通过最小 DTO/项目绑定设计复核，再并行实现。每个任务包附完成条件、失败停止条件和调用预算；阶段零本轮付费 API 预算为 0。真实模型对照属于后续有预算的独立验收。

## 7. 阶段零设计复核处置

v0.1 经 C 只读复核提出 R1 生命周期/派发边界、R2 首次项目绑定并发、R3 预算单位及逐次核算。统筹在 v0.2 分别补入实例+修订元数据及单次派发授权点、session 行锁与运行关系权威规则、明确 16384 UTF-8 字节上限并沿用全量 wire 预算。旧草稿中的 4096 token 初值已撤回，不能在后续任务中混用。此为设计层关闭，不代表代码或验收已实现。
