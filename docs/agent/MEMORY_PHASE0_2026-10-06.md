### 原浏览器失败的说明

原脚本在刷新恢复后，未等待研究列表完成，就计算 `cardsBefore`；本次移动端得到 0，之后定位器点击才等待卡片到达。删除后 `loadedBefore=1 → loadedAfter=0`，但 `cardsAfter=0` 不等于错误基线 `0−1`，因此失败。

保留原始结果与日志。针对性诊断从同一提交的脚本派生，仅执行移动旅程，并在计数前增加 `target.waitFor({state:"visible"})` 和基线正数断言，结果 16/16。证据支持本次失败属于检查脚本的列表加载时序问题；本轮没有修改 Claude 的页面或原检查脚本，不把诊断通过包装成原套件 36/36。

## 5. 阶段一设计与任务边界

统一设计见 [阶段一输入契约 v0.2](MEMORY_PHASE1_INPUT_CONTRACT_2026-10-06.md)。阶段零完成设计，不提前实现或派发阶段一。C 对旧 v0.1 的 [独立设计复核](../../../.codex-handoffs/memory-phase0-20261006/C-design-review.md) 提出生命周期身份、首次绑定并发和预算单位三项意见；统筹在 v0.2 的第 7 节记录处置。只关闭设计歧义，不宣称实现通过。

最小交付：用户显式选择项目 → 创建属于该项目的新研究运行 → 服务端重新选择有效快照 → 在预算内进入真实规划输入 → 捕获输入证明与待办延续控制验证。

- A 唯一编辑运行创建 DTO、项目绑定、幂等、上下文运输和调用边界。
- B 负责快照选取、内容指纹、权限/来源/删除状态重验。
- C 负责实际输入捕获、隔离/撤销/预算负例和独立审查。
- Claude 根据英文契约完成页面接入；只有 injected 状态成立后才更新“尚未传入模型”的提示。

初始建议最多 3 份快照，整个 prior_progress 区 canonical UTF-8 序列化最多 16384 字节，另服从原运行完整 wire 准入和 input/output 预算。旧草稿的 4096 token 初值已撤回，不能把字节数当真实 token。序列化开销、中文边界、逐次调用及快照整体舍弃策略在实现时测试；这些是设计参数，不是已验证效果值。
