# Dify 1.17.0 workflow integration

`deepresearch-evidence-v1.yml` is the production Workflow DSL candidate for Dify 1.17.0. Its DSL version is 0.7.0, the current app DSL version in that local source. It is generated from `build_workflow.py`; regenerate with `python3 integrations/dify/build_workflow.py` and check it with `python3 integrations/dify/verify_workflow.py`. The verifier also checks the fixed `evidence-v1.sample.json` contract sample. The `.yml` file uses JSON syntax, which is valid YAML and preserves Python code node strings without YAML escaping changes. `evidence-v1-fixture.yml` is a separate development fixture that deliberately never publishes an answer.

## Workflow and contract

The graph is Start → Planner LLM → bounded plan validation → initial Worker iteration → evidence validation → Reviewer LLM → optional one revised Worker iteration → Synthesizer LLM → citation validation → End. The no-revision and revised branches each have their own Synthesizer node, so a sufficient review skips the second iteration entirely. Each iteration is configured with `is_parallel: true` and `parallel_nums: 2`. The plan and review validators allow at most four distinct Worker calls combined. They accept only `kb_search`, `web_search`, and `calculator` names present in Java's `allowed_tools` input. Both HTTP nodes have retries disabled. Every logical call gets a deterministic `<java_run_id>:initial:<index>` or `<java_run_id>:revision:<index>` call ID; a retry of the same logical call must reuse its ID.

The Planner, Reviewer, and Synthesizer validators share one strict model-output parser. It accepts a single JSON object, optionally preceded by one complete leading `<think>...</think>` reasoning block emitted by the configured DeepSeek model. Extra prose, code fences, nested or unclosed reasoning blocks, and text after the JSON object fail closed.

The four inputs are `question`, `java_run_id`, comma-separated `allowed_tools`, and optional `session_summary`. The outputs on every branch are `status`, `answer`, `citations`, and `usage`. `status` is `SUCCEEDED`, `INSUFFICIENT_EVIDENCE`, or `FAILED`. `citations` is an ordered, unique array of stable `kb:ragflow:<datasetId>:<documentId>:<chunkId>` IDs. The answer's `[来源N]` markers index that array. `usage` is `{}` because the DSL does not synthesize token accounting; Java obtains usage from Dify run details when available.

The Worker posts `{"runId":"...","callId":"...","input":"..."}` to `POST ${JAVA_INTERNAL_BASE_URL}/internal/dify/tools/{tool}` with `Authorization: Bearer ${DIFY_TOOL_SERVICE_TOKEN}`. The response is `{"success":true,"code":"OK","tool":"kb_search","evidences":[{"citationId":"kb:ragflow:...","sourceId":"来源1","title":"...","content":"...","untrusted":true}],"value":""}`. `web_search` and `calculator` return their result in `value` and no citable evidence. The Workflow treats tool text as untrusted data, rejects malformed evidence and failed tool responses, and only cites validated knowledge chunks. Java still owns the final per-run source whitelist, authorization, cancellation, and result persistence. The Java tool endpoint permits at most six distinct call IDs per run as a defensive upper bound, while this DSL emits at most four.

## Import and configuration

1. Start the local Dify checkout at `/Users/zwy/Claude/Projects/dify` (version 1.17.0). Its local `docker/.env` publishes HTTP on 8081 and HTTPS on 8444; do not use its default 80/443 because RAGFlow uses those ports. Never run `docker compose down -v` against the existing stacks.
2. In Dify Studio, create a Workflow app by importing `deepresearch-evidence-v1.yml`. Select a configured chat model for the four LLM nodes. The DSL pins provider `langgenius/deepseek/deepseek` and model `deepseek-v4-flash`, which is exposed by the locally installed official DeepSeek plugin 0.0.24. Other plugin versions must be checked before import; the earlier `deepseek-chat` model name was rejected by this plugin. Use deterministic/low temperature settings.
3. Set the Workflow environment variable `JAVA_INTERNAL_BASE_URL` to a Java origin reachable from the Dify API and worker containers, with no trailing slash. `host.docker.internal` is a local example and must resolve in those containers. The Dify HTTP Request SSRF policy must permit that specific Java service origin. Restrict the Java endpoint to the Dify service identity and deployment network.
4. Set Dify's **secret** Workflow environment variable `DIFY_TOOL_SERVICE_TOKEN` to the same dedicated 32+ byte opaque value as Java's `DEEPRESEARCH_WORKFLOW_DIFY_TOOL_SERVICE_TOKEN`. The checked-in DSL intentionally contains an empty secret value. Never put a user Bearer token, RAGFlow API key, or internal JWT signing key in the Workflow inputs or exported DSL. Export from Dify without secret values.
5. Publish the Workflow, create its service API App Key, and configure Java's `deepresearch.workflow.dify.base-url` and `deepresearch.workflow.dify.api-key`. Java's `deepresearch.workflow.engine` stays `langgraph` until the joint acceptance gate is complete. The Dify path is available only when explicitly set to `dify`.

Smoke input example for a Java-created run: `{"question":"What does the policy say?","java_run_id":"<Java UUID>","allowed_tools":"kb_search,calculator","session_summary":""}`. The `user` sent to Dify is generated by Java, not accepted from a browser. Do not invoke a published Workflow with a hand-picked `java_run_id`: the Java tool endpoint checks the persisted run, grant, tenant, and tool scope. The separate fixture remains suitable for checking output shape with fixed synthetic evidence.

The current RAGFlow knowledge base is a shared project corpus and has no document-level tenant ACL. Java authorizes each callback against the persisted run owner, requested tool scope, and a dedicated Dify service token; those checks do not create tenant-to-document isolation inside the shared corpus. The RAGFlow gateway admits only locally active documents and verifies each final citation against the current RAGFlow chunk before Java publishes an answer. Missing, deleted, disabled, or unavailable sources fail closed with `CITATION_SOURCE_UNAVAILABLE`.

## Validation status and recovery limits

`verify_workflow.py` checks graph edges, the concurrency setting, tool URL/auth references, bounded plan/revision, fail-closed response handling, no-evidence behavior, and indexed citation validation by executing the actual Code node functions. This is an offline contract check.

Existing Dify runs continue to reconcile after the global engine is switched back to `langgraph`; the engine setting controls admission of new Dify runs rather than recovery of already-bound work. Keep the Dify App Key configured until every admitted Dify run is terminal. Reconciliation uses bounded remote-call concurrency and explicit network deadlines so an unavailable Dify instance cannot indefinitely occupy the scheduler.

Cancellation and timeout revoke Java publication immediately. Remote Dify cleanup is tracked independently in PostgreSQL V15: `PENDING` → `LEASED` → `REQUESTED` after a 2xx stop response, then `CONFIRMED_STOPPED` only after Dify run detail reports `stopped`. `REMOTE_TERMINAL` means Dify finished before a stopped state was observed; `EXHAUSTED` means the bounded retry budget ended without confirmation. An expired lease is retried after a Java restart. The public workflow status includes `remoteStopState`; `CANCELLED` or `TIMED_OUT` alone must not be read as confirmation that Dify stopped. The adapter never automatically redispatches an ambiguous workflow POST.

For Docker Compose opt-in, set `DEEPRESEARCH_WORKFLOW_ENABLED=true`, `DEEPRESEARCH_WORKFLOW_ENGINE=dify`, `DEEPRESEARCH_DIFY_BASE_URL`, `DEEPRESEARCH_DIFY_APP_KEY`, `DEEPRESEARCH_WORKFLOW_DIFY_TOOL_SERVICE_TOKEN`, and the RAGFlow provider settings. The Compose app service passes these through. Keep the default `langgraph` route until the live comparison and fault checks are recorded.
