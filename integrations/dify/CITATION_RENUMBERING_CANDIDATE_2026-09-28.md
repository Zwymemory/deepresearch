# Citation numbering repair rollout — 2026-09-28

The fixed live baseline `0a75f5f` produced a safe business `FAILED` for one positive question. Dify's remote workflow itself succeeded, but the final Code node rejected the Synthesizer output. The evidence context contained nine chunks labelled `来源1` through `来源9`. The answer used marker ordinals `[1,2,2,6,7,3,5]`, while its six declared citation IDs matched the first-used evidence ordinals `[1,2,6,7,3,5]` exactly (6/6). The original validator interpreted markers as positions in the six-item citation array, so `[来源7]` failed. Java's five-citation ceiling would also reject the six-source answer.

The candidate keeps the evidence labels as the model's only numbering scheme. The final Code node resolves each marker against the ordered, validated evidence context; it requires the model's citation-ID **set** to equal those resolved IDs, then derives first-use order itself and rewrites the public answer to contiguous `[来源1]…[来源N]` markers. Unknown ordinals, mismatched IDs, duplicates, more than eight distinct sources, malformed markers, and untrusted extra labels still fail closed. Java independently checks the run receipt allowlist and each source's current RAGFlow state within its existing eight-second deadline. Its citation cap rises from five to eight; the network-call count remains bounded.

Offline reproduction in `verify_workflow.py` covers the observed nine-evidence/six-citation marker sequence, a reordered declared ID list, and both mismatched-ID and out-of-range failures. The completed fixed baseline had 26 successes, 6 failures and 5 insufficient-evidence outcomes across 37 questions. Four failures exceeded the old five-source Java cap; the other two declared the correct source set in a different order from answer marker first use.
